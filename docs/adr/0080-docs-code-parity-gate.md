# The docs-parity gate merges both CLI registration surfaces and scans only fenced shell blocks

Status: accepted

## Context
Any looser heuristic produced false drift against long-standing docs and the CLI's own error messages; the strict declarative extraction costs maintenance of the extraction regexes and the explicit no-op/allowlist tables.

## Decision
The docs-code parity gate fails when user-facing docs drift from the registered CLI, treating the standalone binary and the plugin-runtime commander tree as ONE user-facing surface, and extracting commands only from fenced shell blocks.

Rules:
- A documented `remnic <cmd>` must be REGISTERED in at least one of the two surfaces (the standalone binary's `switch (command)` dispatch and the commander tree rooted at the `engram` parent) — not dispatched by every surface. Ten documented commands (secure-store, recall, tier, backup, console, dreams, patterns, peer, purge, recall-explain) exist only in the commander surface; scoping the gate to one surface would flag all ten as drift against long-standing docs and the CLI's own error messages.
- Commands are extracted only from fenced ```/~~~ shell-like blocks, never inline code spans in prose, tables, or list items — inline code legitimately references MCP tools, session toggles, and planned features that are not CLI invocations; the false-positive analysis across 25 inline-code sites showed scanning them is unreliable without semantic context. Diagram/data/prose fence languages are skipped. The root README is included as the primary user-facing doc (a docs/-only scan would miss its install/quick-start examples).
- The registered set comes from authoritative declarations only: the exact `type CommandName =` union body (sibling unions like DaemonAction would leak members and mask drift like a `remnic install` docs typo; bare `case` labels include nested subcommand arms and are not scanned), `cmd.command("X")` registrations on the root variable only (case-sensitive word boundary excludes tierCmd/namespacesCmd; required/optional arg placeholders inside the command string are absorbed so three real top-level commands are not dropped), and commander receiver variables resolved to correct parent→child paths (the earlier rolling-chain heuristic mis-attributed grandchildren; the gateway prefix is dropped so paths match allowlist format). No-op allowlist entries are explicit, each citing a tracking issue, and function-scoped by brace depth so a marker in a later function is not attributed to a stale handler name.
- Stub detection tests each `static readonly capabilities` flag independently (order-independent — the earlier fixed-sequence regex silently disabled stub detection when keys were reordered) and keeps a legacy inference backstop consulted only when the publisher has not declared `isStub` explicitly. Automation claims are scoped to install sections only (an honest runtime-behavior description is not a false positive); a negator within the 40-char window before a phrase means the claim is DENIED — honest disclaimers do not trip the gate. Host-ID→docs mapping for stub-gated install sections lives in the script.
- Build Week gated commands must use operator-staged datasets: full runs may otherwise auto-select the CLI-managed store, and quick mode is unsafe even with an override because an absent staged path falls back to a bundled fixture — either silently changes the measured workload and invalidates the run receipt. The gate itself is static: no provider, model, network, or dataset calls. Paid-run fences fail closed on shell mutation (`+=`, arrays, declarations, arithmetic, `printf -v`, namerefs): only the exact allowlisted export is valid, while ordinary reads and dependent expansions do not invalidate an export.

## Consequences
See Decision: each rule pairs the constraint that forced it with its cost (extra reads and realpath work, explicit caller options, maintenance of shared helpers and gate regexes). Where topics were merged into this theme as nearest neighbours rather than standalone ADRs, that is noted here: the small single-site topics are absorbed into the theme whose files and failure modes they share.
