# X-ray capture is a best-effort, opt-in side channel whose snapshot must explain every admitted and excluded result

Status: accepted

## Context
Operators debugging a recall need to see what was considered, what was admitted, why results were dropped, and what each served fact derives from — including quarantined items (exclusion must never look like "no result") and peer-profile injection state. Capture runs inside the hot recall path, races with early returns and aborts, and its inputs come from several independently-filtered arrays that must not be zipped positionally.

## Decision
- Capture fires ONLY on explicit opt-in, on every branch including `no_recall` (which captures its own empty-budget snapshot earlier) and the pre-gate point BEFORE the confidence gate can zero the pool; a capture failure must never propagate into recall, and an already-aborted caller must not clobber a prior successful capture.
- Snapshot facts come from the arrays that produced the served results: derive results from `recalledMemoryPaths` (the independent id/path filters would misalign a positional zip), take namespaces from the aligned capture array rather than re-deriving from relative paths, index results by path to pull the per-result explain data actually annotated, and label the serving branch through the same inject-seam annotator.
- `considered` is the PRE-truncation pool size of the branch that actually produced the admitted results (picked by recallSource; fall back to the admitted count when no branch ran), never the max across branches; it must never be less than `admitted` (floor at admitted for self-consistency). An exhaustive switch over recallSource forces a compile error when a new source is added, with a never-typed runtime fallback.
- Quarantined items appear in the snapshot with their exclusion reason; claim-level provenance spans surface the literal source excerpt; per-result trust projection and the servedBy tier mapping are recorded at record time so a published snapshot is born annotated, and the peer-profile injection annotation uses three-state semantics (absent = feature off, null = enabled-but-nothing-injected, object = injected) that never reports injection that didn't happen — cleared when the section is gated out of the rendered context.

## Consequences
Debugging a recall needs no re-run and no code change, and every snapshot is self-consistent. The cost is bookkeeping of pre-truncation pool counters per branch and annotation side-channels, all gated behind the opt-in flag so the default path pays one object allocation.
