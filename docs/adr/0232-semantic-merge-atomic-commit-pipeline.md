# Judge-mediated semantic merges commit through a snapshot-rollback, CAS-receipted pipeline with metadata parity

Status: accepted

## Context
Merging one memory into another mutates the target's body, metadata, graph edges, fact-hash identity and episode ordering, and runs concurrently with other writers. Nine review rounds repeatedly found the same defect class: the merge persist path silently diverged from the create path, and a concurrent write between judge review and commit could make the merged body stand on a stale base. Telemetry also risks leaking fact content.

## Decision
Every merge persists through the same ordered pipeline: snapshot rollback data BEFORE any mutation; refuse or re-check when the on-disk body no longer matches the body the judge was shown (CAS receipt — the merged standing is provably ours only while the base hash matches); inherit and parity-check all create-path metadata (validity bounds, links, navigation, provenance — never upgrade trust/provenance by merging, and fence degraded merges to their pre-merge provenance); rebuild generated graph edges from the merged body under a revision guard so stale rows cannot survive; bind promotion to the record's semantic fingerprint, not its bytes, re-reading with fail-open notices and refusing retired records; persist the merged target move-to-end into the thread's durable episode set; and in shadow mode record the decision only, never mutating. Telemetry logs category, length and reason — never fact content.

## Consequences
A merge is all-or-nothing up to the snapshot; a lost CAS race aborts rather than silently overwriting a concurrent edit. Merges cannot launder weak provenance into strong. Rollback data costs an extra write per merge, and any new create-path metadata field must be added to the merge parity gate or the gate refuses.
