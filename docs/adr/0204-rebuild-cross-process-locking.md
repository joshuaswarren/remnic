# Rebuilds and catalog mutations share one held cross-process mutex

Status: accepted

Rebuild of the namespace catalog (`namespaces.jsonl`) runs in a separate CLI
process from the live gateway, so in-process serialization alone cannot protect
the log. Several race classes forced a single consistent design:

- A rebuild's final `loadCompacted()` -> atomic `rename()` window: an append
  landing inside it is silently overwritten (lost touch).
- A naive serialized chain (bare promise chaining) drops every later section
  after one rejection (poison chain).
- Locks previously used a per-instance owner id, so two calls in the SAME
  process mistook each other's lock for self-held.
- CLI automation needed an honest success signal when a rebuild could not apply.

## Decision

Every catalog mutation (touch, rebuild rewrite) runs inside one shared
mutation serializer (per-instance `queueCritical`), and mutating work
additionally holds the SAME cross-process advisory file lock across its
entire read -> merge -> append / load -> merge -> rename window. Rules:

- The file lock is always acquired INSIDE the in-process critical section
  (consistent `queueCritical` -> file lock order), never around it.
- Lock ownership is per-CALL (owner uuid from the shared util), so no call,
  even on the same instance, treats another's lock as self-held.
- A rebuild's disk scan runs LOCKLESS; the mutex is scoped to the final
  brief load->merge->rename window only. While holding the lock, the rebuild
  heartbeats the lock file's mtime so a long operation is not judged
  stale. Breaking a stale lock re-validates the lock identity immediately
  before unlink and never deletes a replacement lock acquired in the race
  window; it releases only its own lock.
- A rebuild that cannot acquire the lock runs compute-only and reports
  `applied: false`. A touch that times out waiting for the lock DROPS its
  append best-effort: it never appends without the lock, never hangs, and
  never fails the primary memory operation.
- A failed serialized section never poisons subsequent sections; recovery
  is the shared util's contract.
- The CLI reports failure whenever a non-dry-run apply did not apply
  (lock contention or an inert/disabled catalog): `applied: false` sets a
  non-zero exit code, in both JSON and non-JSON modes.

## Consequences

Under lock contention a touch may be dropped (catalog metadata is
best-effort and rebuildable), and a rebuild may report applied:false with a
non-zero exit code. Automation must treat non-zero exit as "re-run later",
not crash. The scan being lockless means a touch can land mid-scan; that is
recovered by the rebuild's under-lock re-merge.
