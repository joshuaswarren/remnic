# Present-but-invalid configuration values are rejected loudly instead of silently defaulting

Status: accepted

## Context
Silent coercion hid configuration mistakes: typos like a misspelled `fallback` key silently dropped a whole fallback chain, fractional values (0.5) floored to 0 and disabled a tier, boolean-ish strings read as truthy and re-enabled disabled features, and a JSON null operator block surfaced as a throw deep inside a resolver. In every observed failure the operator got the opposite of what they asked for, with no diagnostic.

## Decision
Any configuration key that IS present but cannot be understood must be rejected with a loud error; only an absent key (undefined) falls back to its default. Integers must be integers (no flooring or clamping of fractional input), unknown keys are rejected (additionalProperties:false), an explicit null is invalid input (not absent), and non-object shorthand forms like `procedural: false` are rejected. Namespace identifiers are intentionally NOT sanitized at config time: containment is enforced at the filesystem sinks, where an unsafe value surfaces as an explicit error instead of being silently rewritten.

## Consequences
Operators get a hard failure at startup for typos instead of silently wrong behavior. Values that earlier versions accepted silently (0/1 for booleans, fractional counts) now throw and require correction. Validation happens per key, so new keys must pick the strict helper, not an inline truthiness check.
