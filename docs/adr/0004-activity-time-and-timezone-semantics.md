# All activity day windows resolve in the configured timezone with exact, canonical instants

Status: accepted

## Context
Activity artifacts group on a calendar day in the configured activity timezone, but the host-local day drifts near midnight, historical zones carry seconds-precision LMT offsets, some local midnights never occurred (spring-forward) or occurred twice (fall-back), and whole civil dates can be skipped (Pacific/Apia 2011-12-30). TEXT-comparison day windows and content-derived snapshot identities make any non-canonical timestamp or raw-string timezone hash silently wrong.

## Decision
- Every timestamp is canonicalized to `YYYY-MM-DDTHH:MM:SS.sssZ` before day-window range filtering, and impossible capture timestamps (e.g. 2026-02-30, two-digit-year remaps) are rejected rather than silently rolled over by Date.parse.
- Local midnight resolves by probing candidate offsets at full (seconds) precision across the day and the prior UTC day, keeping the EARLIEST instant that lands exactly on local midnight; offsets are derived from the rendered wall clock, never from minute-truncated longOffset strings.
- A skipped or never-occurring local midnight resolves to the first instant whose local date reaches the requested date (binary-searched to the millisecond over a 48h bracket); a skipped civil date keeps a zero-width window and contributes to no daily total — never aliasing the next real day.
- The "today"/--date semantics derive from the configured activity timezone, not the host clock; an explicitly empty --date is invalid, not absent.
- Week/snapshot config identity canonicalizes the IANA zone (case-insensitive; aliases like US/Eastern collapse) BEFORE hashing, sorts category lists without mutating the caller's array, hashes order-independently, and uses fixed field order with JSON.stringify separators so no collision can fork a stored history. The timezone belongs to the source identity: identical observations under a different timezone must not reuse the cached day.
- Chronological ordering compares parsed instants, not raw strings; unsaved snapshots fall back to content hash then app/window for a total order; recap window bounds must be explicitly finite (NaN passes <= checks and emits NaN timestamps); the dashboard derives canonical bounds from the summary regardless of input spelling; the previous-period field is always present, with an explicit unavailable marker so absence is never read as zero; the previous calendar date comes from pure date arithmetic (no DST wall-clock drift).

## Consequences
Correct behavior across historical, half-hour, skipped, and repeated days, at the cost of a probe/binary-search resolver per date. Raw timestamp strings can never be trusted for range filtering or identity.
