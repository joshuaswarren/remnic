# The TUI refresh loop is unkillable by design: latches release in finally, trace writes are fire-and-forget with backpressure, and stop awaits the in-flight tick

Status: accepted

## Context
The operator console renders a fixed one-screen layout on a timer while optionally recording traces to disk. A render exception, a wedged filesystem, or a Ctrl-C arriving mid-tick each previously froze the loop, dropped enqueued frames, or raced a post-close `append` against the closing recorder. Node also exits early if the only ref'd handle disappears, and lingers if a safety-net timer stays ref'd.

## Decision
- Every refresh-cycle error is contained: the tick body runs in try/finally so the `inFlight` latch always releases (a single render exception must never permanently freeze the loop); a throwing renderer falls back to a minimal error frame; aggregator read errors are surfaced without crashing the loop; the loop keeps painting even when a trace append never resolves.
- Trace recording never blocks painting: the tick does NOT await trace writes. Backpressure gates them — while one append is pending, subsequent frames are dropped instead of enqueued, because a wedged FS would otherwise grow the write chain one JSON line per tick until OOM. Drops are counted and exposed (`getDroppedTraceFrames()`, `getLastError()`) so operators can see recording lag.
- Panel lines match the border width exactly (label padded, trailing space before the closing column) so the box edges align; section headers are printed even on error so layout stays stable.
- The refresh interval is deliberately NOT unref'd: a pending promise alone does not keep Node alive, so unref'ing made the console render once and exit. Tests that need exit call `stop()` themselves.
- `stop()` resolves `done` only after clearing the interval AND awaiting any in-flight tick body, guaranteeing any `recorder.append` invocation has at least been enqueued before the CLI's post-`done` `recorder.close()` drains the chain. The fire-and-forget append promise itself is not awaited — shutdown bounding belongs to the recorder's `close()`/`flushWithTimeout`.
- Fire-and-forget tick launchers swallow rejections so the floated promise never becomes an unhandled rejection.

## Consequences
Recording intentionally falls behind (drops frames) rather than freezing the UI or growing memory; the dropped-frame counter is the operator's signal. `done` can add up to one tick of shutdown latency. The unref decision is load-bearing for interactive use — refactoring it for tests would break the CLI.
