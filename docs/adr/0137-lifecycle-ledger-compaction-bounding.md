# The lifecycle ledger is bounded by size-cap-aware compaction that never arms the throttle on incomplete work

Status: accepted

## Context
The memory-lifecycle ledger is an append-only JSONL file. A preserving compaction rewrites it, but three forces fight each other: (1) an encrypted-at-rest ledger becomes unreadable once its on-disk size reaches the whole-file read/decrypt cap — a configured threshold larger than that cap would let it grow permanently unreadable; (2) an encrypted rewrite adds a fixed secure-store envelope on disk, so a plaintext rewrite budget equal to the cap lands AT the cap and retries forever; (3) a min-interval throttle that arms after any compaction would suppress retry of targets that failed, were locked, or were deferred. Pre-fix behavior archived a fresh timestamped backup on every no-op pass, growing the archive without shrinking the ledger.

## Decision
Compaction of a lifecycle ledger must:
- Trigger on the SMALLER of the configured threshold and the decrypt cap for encrypted targets (cap-clamp), so an over-cap encrypted ledger always stays eligible; plaintext targets keep the configured threshold.
- Reserve the secure-store envelope (+1 byte) from the plaintext rewrite budget whenever the REPLACEMENT will be encrypted (the storage write mode, not the current file header), so the encrypted output lands strictly below the cap and the post-write size check cannot fail forever.
- Preserve append-only history frontmatter cannot reconstruct; bounding (overflow into a verbatim timestamped backup), not junk-discard, is what caps the ledger. Nothing is lost.
- Treat a preserving rebuild that reproduces the ledger byte-for-byte as a successful no-op ("compacted"): skip backup+rewrite, still arm the throttle, so the archive stops growing.
- Arm the min-interval throttle ONLY when at least one ledger compacted, nothing failed, and nothing was deferred. A locked/deferred encrypted ledger reports "deferred" (not "skipped") so another target's success cannot suppress it for a whole interval.
- Bypass the throttle immediately ONLY for a target whose ledger is encrypted AND at/over the decrypt cap; below-cap targets, including plaintext oversized ones, stay throttled.
- Recheck the single-flight in-flight guard synchronously right before claiming it (the over-cap probe awaits), so two racing requests never run duplicate 400MB-class compactions.
- Drain each target's durable pending spill into its ledger BEFORE any threshold or throttle return, bounded per queue and never bypassing encrypted-store safety.
- Run this compaction check off the maintenance-request entrypoint, independent of QMD availability, fire-and-forget, never awaited, never throwing.
- Verify after rewrite that the on-disk size is below the cap; an ineffective compaction reports "failed" so the throttle stays un-armed.

## Consequences
Encrypted ledgers can never become permanently unreadable, and compaction work is never silently suppressed — at the cost of an extra lstat/open encryption probe per target and a slightly smaller effective rewrite budget for encrypted stores. No-op passes still count as effective passes, so the archive grows only when content actually changes.
