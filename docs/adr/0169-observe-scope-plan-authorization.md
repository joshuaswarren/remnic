# Observe authorizes once, through a read-only scope plan, before any session mutation

Status: accepted

## Context
Observe writes to several stores (LCM archival, objective-state, transcript, extraction) and mutates session state (coding-context binding). Resolving the writable namespace a second time for the legacy response field re-authorized the implicit default mapping and could REJECT a project-scoped observe the scope plan had already authorized — after the plan had seeded the coding context, leaving an orphaned session binding. Running the plan after attachment, or deriving identity by parsing namespace-prefixed session keys, produced the same class of bug from the other side: provenance collapsed to a default principal and replays resolved different scope than the first call.

## Decision
- The scope plan is observe's single authorization point (rule 22 / 39). It runs READ-ONLY and re-runs the SAME authorization as memory_store/suggestion_submit — the explicit-namespace check AND the coding-overlay self-base canWriteNamespace check — BEFORE any session mutation. Its overlay resolves from the per-call cwd/projectTag fallback, identical to the context that would be attached, so scope is the same either way.
- Every derived namespace is DERIVED from the plan's outputs and never re-authorized: the legacy `namespace` response field (explicit namespace, else config.defaultNamespace for user-project overlays; hosted scope-profile layers report their effective profile write namespace), the LCM archival key, the objective-state namespace, and the extraction storage target.
- Coding-context attachment (auto-resolve from cwd/projectTag so later bare recalls are project-scoped) happens only AFTER the plan authorizes the write; a rejected observe leaves NO coding context bound to the session.
- Extraction separates IDENTITY from STORAGE ROUTING. Storage is pinned to the plan's effective write namespace via writeNamespaceOverride — pinned ALWAYS, including when namespaces are off (the resolved value is the collapsed default store), so a later namespaces-on restart cannot retarget accepted captures, and so extraction cannot re-derive (and miss) the overlay. Identity uses the ORIGINAL sessionKey for provenance threading plus principalOverride pinned to the plan's resolved principal (auth precedence applied); a namespace-prefixed key matches no prefix rule and mis-derives the principal to default. Current policy is re-authorized against the ORIGINAL project binding. principalOverride is omitted when no principal resolved, preserving namespaces-disabled behavior.

## Consequences
One authorization path to audit; rejections can never strand session state; duplicate (and divergent) namespace resolution is gone; accepted captures keep their original storage target across config changes; identity parsing never runs on routing strings.
