# Gateway-routed models use provider-qualified routes; the base model stays direct-compatible

Status: accepted

## Context
Direct-key call sites pass `cfg.model` straight to the OpenAI Responses API, so a provider-qualified route string there is unroutable. Conversely, gateway-routed call sites given a bare id (including the `"gpt-5.5"` schema default OpenClaw injects when an operator only configured modelSource + taskModelChain) resolve to an unroutable `<provider>/gpt-5.5`. A stale process-level OPENAI_API_KEY could also be implicitly captured in gateway-only deployments, making diagnostics look OpenAI-dependent.

## Decision
`cfg.model` must always remain a bare, direct-compatible model id; it is never rewritten into a provider-qualified gateway route string, even when a task chain is configured. Gateway-routed surfaces (summary model, recall planner, flush plan, hourly-summary cron) resolve through the configured task chain (explicit summaryModel, then explicit base model, then gateway task-chain primary, then empty so the gateway default wins), dropping bare ids in gateway mode. A gateway model string must be `provider/model` with non-empty segments, validated at config time so a model the runtime would silently drop is rejected early. Gateway mode never implicitly captures OPENAI_API_KEY; operators opt out explicitly. The default reasoning model id is centralized in one constant shared by all LLM-backed surfaces, and new surfaces use the routing alias `"auto"` rather than a hardcoded id.

## Consequences
A bare schema default leaking to the gateway would produce silent unroutable calls; the cost is that gateway-routed models can never inherit cfg.model directly. recallPlannerModel intentionally does not inherit cfg.model. Sibling packages may keep their own model constants only when scoped to their own subsystem.
