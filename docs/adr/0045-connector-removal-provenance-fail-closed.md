# Connector removal fails closed on lost or malformed install-time provenance

Status: accepted

## Context
Connector installers record where they put files (proxy configs, plugin shims, registry entries) in a per-connector config under the user's control. That record is the only map from an install to its on-disk artifacts. Environments change between install and remove (REMNIC_HOME/HERMES_HOME rotated or unset, XDG_CONFIG_HOME changed, JSON hand-edited). If removal silently re-derives paths from the current environment, it can delete the registry entry and then miss the real artifact — orphaning files that may still hold a live bearer token — while reporting success. Conversely, treating a plain config that merely lacks provenance fields (a legitimate pre-#1929 install) as corrupt would break cleanup for old installs.

## Decision
Connector removal must treat install-time persisted state as the sole source of truth and fail closed when it is unusable:

- Read persisted paths (e.g. `proxyConfigPath`, shim locations) BEFORE deleting any registry config; removal targets the persisted absolute path, never a recomputation from the current environment. Env-derived paths are a fallback only for legacy installs that pre-date provenance fields.
- If a config file exists but fails to parse, abort the entire removal, leaving the config and artifacts untouched so the operator can inspect/fix and retry. Never unlink a malformed provenance record.
- Best-effort token revocation runs first so an orphan token cannot outlive a partial cleanup, and the reported status must state truthfully whether the token was revoked (never a hardcoded "token has been rolled back").
- Extension/config removal is ordered so that the provenance-bearing config is deleted only after artifact removal succeeds; a failed artifact unlink surfaces `status:"error"` instead of pretending success, because a retry would take the `not_found` path once the registry is gone.
- Removal of a config that has no provenance evidence it manages the artifacts is skipped rather than guessed.

## Consequences
A malformed registry config blocks automated removal until an operator fixes it — deliberate, since proceeding risks orphaning live tokens or destroying the only retryable provenance record. Removal is no longer idempotent-by-recomputation: it depends on install-time writes surviving intact. Failures after partial progress must be reported as errors so automation flags them.

## Merged themes
`weclone-remove-safety`, `hermes-remove-preflight`, `weclone-persisted-proxy-path`, `weclone-remove-failure-surfacing`, `weclone-token-rollback-truthful-status`, and `weclone-proxy-config-atomic-rollback` records are merged here: they all instantiate the same rule — persisted provenance wins, parse failures abort, errors surface truthfully.
