# Auto mode delegates only to a verified same-corpus daemon, discovered the way the server discovers itself, under one shared probe budget

Status: accepted

## Context
The OpenClaw bridge's `auto` mode must decide between running an embedded orchestrator and delegating to an already-running daemon. Guessing wrong in either direction is destructive: a second orchestrator boots on the same corpus, or auto stays embedded beside a healthy daemon. The decision surface is hostile: wildcard binds and the machine's own NIC/VIP addresses make raw address comparison wrong, config files exist in multiple locations and generations (systemd units, drop-in overrides, legacy names), tokens differ per config and rotate, and candidates can accept connections and never answer, stalling a naive probe past its deadline.

## Decision
Role split: the detector answers only "is a healthy same-corpus daemon here?" — the caller owns explicit overrides. Without a corpus it can verify against, `auto` stays embedded rather than guessing.

Same-host classification must handle the real address space: `0.0.0.0` and wildcard binds are same-host; the machine's own interface/VIP address and its IPv4-mapped IPv6 spelling are same-host and dialed through loopback first, with the configured address as fallback; loopback-shaped DNS names that merely pass a prefix test are not accepted, and routable v6 literals are remote. Same-host aliases are two dial addresses for ONE candidate — budgeting them separately halves the effective allocation and times out healthy daemons.

Corpus match: compare health's namespace-resolved storage dir, canonicalized on both sides, on real existing directories — symlink escapes fail closed, and a corpus root that is itself a link is a mutable trust anchor. The capture buffer is bounded, and a value that does not fit reads as unknown, because a truncated path would look like a different corpus.

Discovery mirrors the standalone server exactly: cwd before home, reading both canonical and legacy unit pairs (the running one may live outside the ordinary discovery list), `systemctl` drop-in overrides (`<unit>.d/*.conf`), every home-reference form expanded (a literal `$HOME` once passed through unexpanded and hid the daemon), the cwd file winning as a whole (no splicing fields across files), the process's own `REMNIC_CONFIG_PATH` still outranking everything, and server environment merged over file only where the server does so. A config file the daemon's own loader rejects is not the one it booted from; adopting its defaults probes the wrong port.

Auth binds per endpoint: each candidate uses its own config's token, overridden by a gateway-store token when present, and never falls through to another config's credential; a config with no token means that daemon runs unauthenticated. Endpoint-only dedupe is wrong when two configs share host:port but differ in token; delegated requests re-read rotated tokens instead of caching.

Probing: one shared deadline divided across real candidates only — endpoints already classified as skipped remote stay out of the divisor, aliases share one share, and each stalling candidate burns at most one share, so the live candidate behind stallers is still reached inside its own. Readiness retries are bounded by the same deadline (a permanently unready daemon must not hold registration open), zero or negative budgets are rejected at the boundary (they would silently select embedded), and the capture probe must signal on post-header completion too — a probe watching only pre-header failures blocks the synchronous caller for its whole slice.

## Consequences
Auto mode never double-boots an orchestrator and never strand-embeds beside a healthy daemon, but the detector must continuously mirror server-side discovery and auth rules — any server behavior change (new config location, env merge, token rotation) must be reflected here, and probe budgeting constants need headroom so a loaded machine cannot turn a pass into a failure.
