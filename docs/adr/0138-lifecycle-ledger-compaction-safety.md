# Lifecycle ledger compaction preserves every historical row, holds the cross-process lock in write mode, and never downgrades encryption at rest

Status: accepted

## Context
The memory lifecycle ledger is append-only history that grows past the whole-file read/decrypt cap (#2033) and must be compacted. Naive compaction had three failure modes: a rewrite racing a concurrent append clobbered newly appended events (issue #1910); rebuilding from frontmatter alone silently dropped append-only rows frontmatter cannot reconstruct (explicit_capture_accepted, imported, promoted); and rewriting an encrypted ledger as plaintext - or byte-copying an AAD path-bound ciphertext to the archive path - defeated encryption-at-rest or orphaned overflow rows.

## Decision
(1) WRITE mode holds the shared cross-process ledger lock (the same lock lifecycle appends take, with an acquisition budget of twice the stale-break window) across the preserve-read and atomic rename; a lock acquisition timeout REFUSES the unlocked fallback rather than racing. DRY RUN takes no lock and never rewrites, so previews never block appends. Because the CPU-bound merge blocks the event loop and the lock heartbeat cannot refresh, the lock is re-asserted immediately before the destructive rewrite: a LOST lock aborts; a held lock is re-stamped so the write cannot be judged stale mid-rename. (2) Compaction merges the frontmatter reconstruction with the CURRENT ledger read under the lock (through the uncapped buffer path, so an oversize encrypted ledger stays readable): non-frontmatter-derived rows are always carried over deduped by eventId; a frontmatter-derived row collapses only when the scan reproduced the same logical event (same memoryId, eventType, timestamp), otherwise it is preserved deduped by content key; if the existing ledger genuinely cannot be read, ABORT rather than rewrite from frontmatter only. (3) The rewritten ledger is bounded under the read/decrypt cap whenever a cap is set - even when the current ledger read as empty - with the plaintext payload bounded and the secure-store envelope reserved whenever the REPLACEMENT will be encrypted (willEncryptStateWrites), exactly as auto-compaction does. Overflow rows survive in a verbatim timestamped backup (re-encrypted under the backup path's own AAD when the source is encrypted) and, for frontmatter-derived rows, in the memory files. (4) An already-encrypted ledger (or backup) is ALWAYS rewritten encrypted, even when encrypt-on-write policy is paused - compaction must never downgrade encrypted state to plaintext; plaintext keeps ordinary policy. (5) Skip the backup+rewrite when it would change neither the logical (decrypted) content nor the at-rest format (no-op guard against unbounded archive growth); absent ledger reads as ENOENT (a create is a real change); other read errors propagate; buffers are compared as bytes, never decoded to one giant string. (6) Ledger readers admit any structurally valid row (permissive eventType) and sorting is total across unknown types; ledger streaming aggregates inline so heap is O(phases), and the dreams ledger closes the readline interface AND destroys the underlying stream so early-exiting consumers release the file descriptor. Dreams ledger validation: required fields must be present and correctly typed; optional fields may be absent but a present wrong-typed value marks the row malformed (skipped, never coerced). Dry-run phase telemetry must be backed by the orchestrator phase runner for live runs so the command never reports success without executing the phase. Projection timeline assembly streams the ledger one event at a time with dedup and interns repeated scalars.

## Consequences
Write-mode locking serializes compaction against appends; byte-capping drops oldest rows from the active ledger (recoverable from backup/files); re-encrypting backups couples the backup format to the secure-store AAD scheme; the strict abort-on-unreadable rule means a corrupt ledger blocks compaction until repaired.
