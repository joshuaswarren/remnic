# The Hermes `remnic:` config block is written under the resolved Hermes home with guarded YAML and 0o600 token files

Status: accepted

## Context
Remnic injects a `remnic:` block into Hermes' config.yaml. Upstream Hermes resolves config.yaml relative to `get_hermes_home()` (honoring HERMES_HOME and the platform default), so writing the block under a hard-coded `~/.hermes` while HERMES_HOME points elsewhere would be silently ignored. The block carries a bearer token, and its values are interpolated into YAML by hand. Additionally, legacy alias layouts symlink `profiles/default/config.yaml` onto the root config, and users may have user-authored content in plugin directories.

## Decision
- The `remnic:` block is rooted at the SAME Hermes home the shim uses (HERMES_HOME-resolved, platform-native default) — never a hard-coded path.
- Scalar values interpolated into the block are validated first (`sanitizeHermesHost/Port` throw on anything that could break out of the scalar context); the randomBytes-generated token is additionally guarded even though it is safe by construction.
- Updates replace only the host/port/token sub-keys of the existing `remnic:` section (matched from `^remnic:` to the next top-level key or EOF); other keys under `remnic:` are preserved. Files are normalized to end with exactly one newline.
- Files holding or having held a bearer token are created and rewritten at 0o600 (temp-file + rename) so a rewrite never temporarily widens permissions under a default umask.
- Symlinked components below the Hermes root must not redirect the token-bearing write; defense-in-depth checks keep the resolved path under the expected root.

## Consequences
Rewriting YAML by hand requires careful scalar validation and newline handling; a foreign YAML parser is not introduced. Token files stay 0o600 forever once tokenized, even after the token is removed. Writes to unexpected symlinked locations are refused rather than followed.
