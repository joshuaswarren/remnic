# The on-disk directory scan is authoritative for which namespaces exist, and catalog roots must match the runtime router

Status: accepted

Rebuild reconstructs the catalog from disk plus a log that may contain stale
or concurrent rows. Without a single authority, deleted namespaces get
resurrected from stale log rows, live namespaces get purged because the scan
snapshot missed them, and cataloged storage roots drift away from the roots
the runtime router actually resolves.

## Decision

For a mutating rebuild (`--apply`):

- The directory scan is the single source of truth for which namespaces
  EXIST. A namespace absent from the rebuilt set is purged, even when a
  concurrent touch on it appears in the final re-merge log — a touch on a
  removed root must not resurrect the row.
- Exception (created-after-scan): before purging, re-check the namespace's
  storage root on disk NOW, with the same symlink/realpath/containment +
  memory-data safety as the scan. Root exists with data -> keep (created
  after the scan snapshot); confirmed absent -> purge. The key from the
  untrusted log is first re-validated with the same safety gate the scan
  uses (default namespace exempt), so a tampered unsafe row is dropped, not
  resurrected.
- Catalog storage roots must equal the roots the runtime router resolves:
  seed configured namespaces with the router-resolved root (legacy raw-name
  dir when it exists, tokenized dir otherwise), never a blanket tokenized
  guess; the default namespace's root comes from the shared
  `resolveDefaultNamespaceRoot` helper the router itself uses, and a
  tokenized default dir must never overwrite it. When both a legacy
  raw-name dir and a tokenized dir hold data for one namespace, prefer the
  TOKENIZED root, matching the router — never last-readdir-wins.
- A scanned root counts as holding data when its markers match the router's
  storage-presence check, including the `state` runtime child; a malformed
  marker (a `facts` file or symlink instead of a real directory) rejects the
  whole root rather than cataloging a root downstream scanners will throw on.
- A dir literally named like a canonical token decodes back to its identity
  EXCEPT when a configured name or an existing cataloged row that owns that
  exact root already claims it — then keep the literal name so one physical
  root never gets two catalog rows.
- A touch with no explicit storageDir records the same on-disk root the
  router resolves (the legacy raw dir when that is where data lives).
- Token-shaped raw namespace names are preserved verbatim by catalog writes.
- The rebuild result also purges a dynamic namespace whose on-disk root was
  deleted and never re-adds it from a stale log row.

## Consequences

Rebuild may drop a row for a namespace whose root is temporarily unresolvable
(symlink/escape) — intentional. Disk reality, not the log, decides existence,
so consumers (maintenance/QMD) never see namespaces the hot paths reject or
miss ones the router actively serves.
