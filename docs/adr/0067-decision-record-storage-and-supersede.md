# Decision records use a strict sealed-envelope write, a permissive parser, and a collision-guarded supersede flow that mirrors lifecycle status into frontmatter

Status: accepted

## Context
Decision records are markdown with a hand-written YAML frontmatter subset, round-tripped through serialize/parse, and superseded rather than deleted. Operator typos, quoting bugs, and lifecycle interactions (tombstones, generic memory status) corrupted decision history or hid records from listings and recall.

## Decision
- Storage contract: pure storage module; the body is preserved byte-for-byte and not introspected (format-neutral round-trips stay open). Frontmatter scalars stay single-line: escape backslashes and double quotes, emit real newlines as `\n` escapes (order matters on decode: backslash-pair first), which keeps the line-based parser safe and diffs friendly. Unexpected frontmatter keys surface early — silent drift is the worst case. Flow-list elements escape embedded quotes and the parser is backslash-aware (track the escape state so `\"` inside a quoted element is not a closing quote). The parser is intentionally permissive about on-disk shape: a record with `status: "superseded"` and no `supersedes` field is the canonical shape applySupersede writes (the supersede edge lives on the replacement) and must stay round-trippable — only `listActive` excludes superseded records, never the parser. The round-trip contract is "each record parses without throwing", not byte identity (`supersedes: undefined` vs key-absent differ under deepEqual). Trailing newline keeps files POSIX-well-formed.
- Status semantics: the default for a record omitting `status` is the least-privileged "proposed" (rule 48); the "active" status set is defined in one place and reused by standing-decision lists, briefings, search, and the OKF export's architecture-card classification (rule 53 — single classification source).
- Supersede: write the replacement BEFORE mutating the old record's status (rule 25) — a frontmatter-write failure leaves a harmless duplicate, not a missing record; the failure is logged but the replacement is not rolled back. A replacement id colliding with an unrelated existing record MUST throw (operator typo / MCP rename; the caller picks a fresh id and retries) — otherwise an unrelated decision is silently overwritten by a record superseding itself. The only allowed collision is `replacement.id === targetId`: the in-place body swap keeps its listing position and carries the supersede edge back to the old body. If the replacement matches a tombstone (pending_review), abort — do not archive the old record; superseding with a non-active replacement would retire the only active decision.
- Lifecycle mirroring: persist decision lifecycle in BOTH places — `structuredAttributes.decisionStatus` is the authoritative decision marker (mirrored from the serialized body, on the replacement too, so list/get projection and QMD indexing agree) and `frontmatter.status` is set to "archived" for inactive decisions (rejected/superseded) so recall/search/maintenance exclude them exactly like a supersede. Conversely, any non-active outer frontmatter status (archived, superseded, forgotten, rejected, quarantined, pending_review) hides the decision from listings until the generic lifecycle resolves. The schema advertises `supersedesId` and treats it as an alias for `id` when `id` is absent. Whether decision records are active for an operator has one source of truth: the coding-knowledge feature gate (rule 39). Operator/API-built records use strict sealed-envelope compose (#1989) — envelope-owned fields ride the envelope, status/connector extras stay explicit. The updated timestamp of a retired record reflects when it was retired, not when it was recorded.

## Consequences
- Strict compose makes invalid machine-built records hard failures rather than repairable drafts; permissive parsing means shape drift appears only in listing filters, never as parse errors.
