# Git origin URLs normalize to stable project ids; git-context resolution never throws and its cache never serves a stale branch

Status: accepted

## Context
projectId drives namespace isolation; divergent parses of ssh://, scp-like, IPv6, file://, port-bearing, and Windows-drive-letter remotes false-coalesced separate repos or split identical ones. Resolution costs up to five git spawns per call, tempting caches that could pin a stale branch after a checkout.

## Decision
- Normalize remote URLs deterministically: protocol-prefixed forms (ssh/https/http/git/file) are parsed FIRST so scp detection cannot swallow an ssh:// URL bearing a port. Ports are preserved in the output — two repos on one host under different ports must get distinct project namespaces. IPv6 is detected via the bracketed input form BEFORE stripping brackets, so re-attached ports preserve the `[host]:port` boundary and `host:2222` stays distinct from a longer bare address; bracketed scp and ssh:// forms of the same remote produce identical ids. Trailing `.git` is stripped case-insensitively (the whole result is lowercased). `file:///path` has an empty host and normalizes under a stable `localhost/<path>` prefix — two distinct local paths never collapse. scp paths may start with digits (no numeric guard; port-bearing URLs matched the protocol branch already). Single-character SSH host aliases (`h:foo/bar`) are accepted — Windows drive letters are filtered first as exactly one ASCII letter followed by `:/` or `:\`. Protocol-like leftovers (e.g. `file` misparsed as an scp host) are rejected.
- `resolveGitContext` never throws: the whole body is wrapped so homedir failures (unset HOME), custom invoker raises, and any future helper error map to "not in a repo" (null). The branch is named by git itself, not a regex over HEAD (a tag sharing the name must not win). projectId derives from a non-cryptographic stable FNV-1a hash of the normalized origin.
- Caching: results are shared across calls, but a hit is served only while HEAD is byte-identical to what git answered for; HEAD is snapshotted once git names the root and BEFORE the branch probe, so a checkout racing the probe leaves the entry older than HEAD and re-resolves — never a stale branch pinned to a new HEAD. Negative-only caches never hold a branch, so snapshots taken from them cannot carry one. A cache hit must not mask cancellation or deadline exhaustion. Timeouts and spawn failures are not answers about the repo and are never cached.

## Consequences
- Caching trades freshness for spawn cost: a checkout racing a probe costs one extra full resolution, never a wrong branch.
