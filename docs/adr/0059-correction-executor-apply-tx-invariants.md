# Correction applies are serialized, non-destructive transactions ordered write-before-retire

Status: accepted

## Context
The correction executor is the only writer for corrections, and it mutates durable memory state across several phases (replacement writes, retirement, tombstones, propagation, plan consumption). A crash, cancellation, or concurrent retry mid-apply could duplicate replacements, leave orphan facts that supersede nothing, resurrect superseded content, or let a tombstone-persistence failure destroy the source. Plan ids and LLM-supplied category values also flow into filesystem paths, so unvalidated values could escape the corrections directory.

## Decision
Every plan apply runs under a per-plan mutation lock. The plan is marked `applying` BEFORE any mutation, inside the lock; a plan that is `applying` or consumed is never re-applied wholesale, and only cancellation before the first mutation resets it to `pending`. Phase order is fixed: (1) write replacement state first — if the replacement write fails, the loser is not superseded; preflight the loser before writing so a deleted loser cannot gain an orphan replacement; (2) write the tombstone BEFORE retiring the source memory, carrying the canonical contentHash and full supersession-key set, so a tombstone failure leaves the source active with no resurrection window; once the tombstone append succeeds, cancellation cannot prevent retirement; (3) propagation is best-effort and recorded as a warning, never a failed action; (4) markConsumed failure after successful applies is a warning, not an error — a client retry must never re-apply corrections. The destination namespace of a rescope is authorized against the write ACL before the move (canWriteDestination defaults to allow in single-tenant use), and the DESTINATION memory id is reported and propagated in its namespace, with the source id retained for source-side propagation. Plan ids that would path-traverse out of the pending directory, and path-like memory categories, are rejected before reaching storage.

## Consequences
A tombstone for a still-active memory (retire later failing) is accepted as benign — it blocks re-ingestion of the same content. Partially applied plans are not retryable and require operator reconciliation via TTL discard. The `applying` marker plus lock means concurrency costs a serialized second-apply rejection rather than silent duplication. If the plan cannot even be marked in-progress, the executor fails closed before any mutation.
