# Connector bearer tokens live only in tokens.json; installs roll back atomically and removal fails closed

Status: accepted

## Context
Early connector installs wrote bearer tokens into connector.json, which `remnic connectors list --json` printed verbatim - leaking live tokens into shell history, CI logs, and telemetry - and generated token entries even for connectors with no auth requirement. Failed installs left rotated tokens with no matching config, and removal paths substring-matched human-readable messages or trusted malformed config payloads.

## Decision
Tokens are stored exclusively in tokens.json (0o600); connector.json never contains one, any stray `token` key is stripped before persisting, and legacy on-disk copies are redacted on read without rewriting user files. Only connectors whose manifest sets requiresToken: true get a token entry; token generation is idempotent under force-reinstall; token-store writes use full-store snapshots so any partial write is atomically unwound; token write errors degrade gracefully (install proceeds, user can generate later) EXCEPT when the connector requires a token and none was produced - the install aborts rather than reporting success without a working credential. Error reporting must be truthful and structured: rollback success/failure is tracked and reported, non-token connectors never emit a token-rollback suffix, and gates use explicit structured flags rather than substring-matching message strings. Install rollback mirrors this: if the config write fails after token rotation or extension install, the token store is restored from the snapshot and a pre-existing customized extension is restored from backup (never deleted); internal/test-only config keys are denied from persistence; the saved config records the resolved codex home and coerced installExtension flag so later removal can match provenance; removal reads the saved config BEFORE deleting anything and fails closed (skips extension removal) when the config is unparseable or a non-object. Built-in connector manifests always take precedence over stale persisted registry entries; only unknown (user-added) IDs are preserved from the file. Structured error fields, not human-readable text, are the contract for tooling. The WeClone proxy config is written to a stable persisted path (never re-derived from a changed env on reinstall) before the registry write, with its own pre-write rollback closure; the generated token is persisted into the proxy config so the proxy authenticates without a second lookup. Hermes profile config writes are 0o600 because they may embed tokens.

## Consequences
Token handling adds a second store that must stay consistent with connector.json across install, reinstall, and remove; every new write path needs a snapshot-and-rollback story. Fail-closed removal means a corrupted connector.json disables automatic extension cleanup for that connector.
